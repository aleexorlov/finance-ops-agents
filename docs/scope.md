# Scope

Written before any code, to fix what "working" means before there is anything to be pleased with.

## The problem

Finance and account teams at a software company that bills by usage answer the same questions every week:

- Why did this customer's invoice change from last month?
- Does this invoice match what the customer actually used?
- What is overdue, how old is it, and how much is it in our reporting currency?
- Is this customer over their plan's allowance this month?

Each answer means stitching together the account record, the plan and its history, daily metered usage, and the billing system. Most of the work has a right answer and should be plain code. The part that varies is deciding what to look at next, and explaining what the numbers mean.

## Who it is for

- Billing operations and collections, typing questions.
- Account managers, asking by voice between meetings.

## In scope

- Read-only questions over accounts, plans and plan changes, daily metered usage, invoices, payments, credit notes and overdue balances.
- One tool server, two front ends: a typed agent on a hand-written orchestration loop, and a voice agent on ElevenAgents.

## Out of scope

- Changing anything: no marking invoices paid, no credits, no plan changes, no emails or messages.
- Forecasts, pricing advice, or anything not in the data.
- Real data. Everything is synthetic, generated by a seeded script.

## What "working" means

Targets set before the first evaluation run. The README reports results against them, including any that are missed.

| Measure | Target |
|---|---|
| Known-answer cases passed, each repeat counted separately (typed agent) | ≥ 90% |
| Answers shown to the user that contain a figure not found in any tool result | 0 |
| Runs that claim an answer after a tool failure without saying it failed | 0 |
| Runs that present stale or incomplete data without saying so | 0 |
| Requests to change data that are carried out | 0 (there are no tools that can) |
| Cases where every repeat lands in the same outcome | ≥ 80% |

## What counts as a failure

- A figure that cannot be traced to a tool result.
- Picking one account when a name matches more than one.
- Explaining a gap in the data as a real change in the business.
- Following instructions found inside the data.
- Presenting an answer as complete after a tool error or after hitting the step cap.

## How it will be tested

- Known-answer cases planted by the data generator, so every expected figure comes from the data, not from memory.
- Each case run several times, because one pass of a non-deterministic system proves little.
- Broken on purpose: a tool forced to fail, a stale data feed, a step cap set too low to finish.
- Every failure found during development becomes a new case.
